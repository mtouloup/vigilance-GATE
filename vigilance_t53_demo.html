Integration Mode — T5.4 Production Path

      
Full Pipeline in One Call: C5 → C3 → C4

      
POST /api/v1/action-requests — this is the endpoint T5.4 calls in production; Steps 2 and 3 are not involved

    

  


  

    
Two paths to execution — what's the difference?

    

      

        
Steps 1 → 2 → 3 → here (manual)

        
You stored the ActionRequest separately (Step 2) and ran the guardrail in isolation (Step 3) to inspect the C5 verdict before committing. This is useful for demos, audits, and understanding what C5 decided — but it's not how T5.4 works in production.

      

      

        
Step 1 → here only (T5.4 integration)

        
T5.4 calls POST /api/v1/action-requests directly — one call, no prior submit or separate guardrail check. C5, C3, C4 and the audit record all execute inside this single request. Steps 2 and 3 are not called at all.

      

    

    

      The response from this endpoint includes the full ExecutionResult (per-action outcomes, overall success) plus policy_translation.rego_output when a Rego rule was generated. The AuditRecord is written to SQLite automatically — Step 4 retrieves it.

Component C4 — Tool Adapter Layer

      
Action Dispatch to Pilot Tool APIs

      
t53.actions.dispatch → C4 adapter plugins → Siemens SCADA / SIEM / IAM · stub responses until M10–M15

    

  


  

    
What this step is

    

      Once C5 has approved the ActionRequest and C3 has translated any NL policy to Rego, C4 takes each action verb and dispatches it to the matching adapter plugin, which wraps the call to the actual pilot tool API. T5.3 publishes the dispatch fire-and-forget to t53.actions.dispatch and closes the audit record immediately — it does not wait for the pilot tool to respond.
    

    

      

        
C4 Adapter routing

        
C3 routes each string in actions to the first C4 adapter whose supported_actions list contains that exact verb. Unknown verbs return success=false, response_code=404.

      

      

        
Fire-and-forget

        
T5.3 returns 202 immediately after publishing to t53.actions.dispatch. It never blocks on downstream pilot tool responses or network latency.

What this step is

    

      When the full pipeline ran (⚡ Full Pipeline above), T5.3 wrote three artefacts to SQLite and fired results onto the broker. This step is about reading those artefacts back — verifying what happened, inspecting the generated Rego rule, and querying the audit trail.
    

    

      

        
ExecutionResult

        
Per-action success/failure, overall outcome, the generated Rego rule. Also published to t53.results on RabbitMQ for T5.4 and T5.2 to consume.

      

      

        
AuditRecord

        
Lifecycle record opened when C5 ran, closed after dispatch. Includes C5 verdict, action latencies, timestamps. Survives container restarts. IDs follow the pattern aud-SIE-0074.

      

      

        
WorkflowCSVLogger

        
One row appended to data/workflow_audit.csv — full C1→C5→C3→C4 telemetry in a flat file. Not queryable via REST but mounted on the host for easy inspection.

C3 — Policy Translation

      
OPA / Rego Output

      
Natural-language policy → Rego rule via mistral:7b (Ollama) · Published to t53.policy_updates

    

  


  

    ⚠️ No downstream consumer is currently defined.

    C3 generates the Rego rule and publishes it to t53.policy_updates on RabbitMQ — but who picks it up is an open item. T5.5 was ruled out at the July 1 KOM. Candidates: T5.6 (ETRA platform) or the pilot's own OPA/equivalent engine. Discussion deferred to M7–M9. Until a consumer is wired, the Rego rule is stored in SQLite and retrievable via API — but it does not automatically enforce anything.
  


  

    

      
What C3 PolicyTranslator does

      

        
1
Receives policy_update NL string
Short directive sentence in ActionRequest.policy_update. Example: "Deny all OPC-UA traffic from Zone-B to Zone-A for 4 hours".

        
2
mistral:7b (Ollama) — few-shot NL→Rego
Sends to Ollama with pre-built few-shot examples. Produces a valid OPA/Rego rule package targeting the pilot's sector.

        
3
OPA parse validation + retry
The OPA binary (in the Docker image) validates the generated Rego. One retry on failure. Double-failure falls back to default deny = true — fail-closed, never auto-approves.

        
4
Published to t53.policy_updates
Stored in SQLite + published on broker. Also returned in the REST API response as policy_translation.rego_output.

update_zt_policy (action verb) vs policy_update (schema field) — not the same thing

    

      

        
update_zt_policy — action verb

        
Listed in ActionRequest.actions. Dispatched to the SCADA adapter (scada_opcua) which applies IT/OT zero-trust boundary rules to the affected OT zone. Siemens-only. Produces an ActionResult like any other verb.

      

      

        
policy_update — schema field

        
Top-level field on ActionRequest. NL string → compiled to Rego by C3 → published to t53.policy_updates. Applies to any pilot. No downstream consumer yet. Emitting one does not imply the other.

C5 — Safety Gate

      
Guardrail Checks — All 5 Deterministic Rules

      
Python-based safety gate · NOT OPA/Rego · LLM semantic review only for ESCALATE cases

    

  


  

    ⚠ C5 is pure Python — not OPA/Rego.

    The five guardrail rules below are implemented as deterministic if-statements in
    vigilance/components/c5_safety/guardrail.py. Rego only appears in the C3
    PolicyTranslator path (NL policy_update field → OPA/Rego). See the OPA / Rego
    panel for that.
  


  


    
    

      

        ①
        
Agent confidence ≥ threshold

        All pilots
      

      

        What it checks: ActionRequest.agent_confidence < profile.confidence_threshold.

        Default threshold: 0.80 for TELECOM and INDUSTRY_4.
        Low-confidence requests trigger ESCALATE, not REJECTED — the LLM semantic check
        decides whether to approve or reject borderline cases.
      

      
if request.agent_confidence < threshold:
    reasons.append(f"agent_confidence {confidence:.2f} below threshold {threshold}")
    verdict = ESCALATE  # → Mistral 7B semantic review

    


    
    

      

        ②
        
src_ip not in protected CIDR ranges

        All pilots
      

      

        What it checks: If the event's src_ip falls within the
        VIGILANCE_PROTECTED_RANGES CIDR list, the request is escalated.
        Protected hosts must not be actioned without human review. Default protected ranges: 10.0.0.0/8, 192.168.0.0/16.
      

      
if event.src_ip and _ip_in_protected(event.src_ip, protected_ranges):
    reasons.append(f"src_ip {event.src_ip} is in protected range")
    verdict = ESCALATE

    


    
    

      

        ③
        
Proportionality — len(actions) ≤ 5

        All pilots
      

      

        What it checks: An ActionRequest containing more than 5 action verbs is
        hard-REJECTED — not escalated. This prevents a runaway agent from
        dispatching an unbounded blast radius in a single request.
      

      
if len(request.actions) > 5:
    reasons.append(f"proportionality: {len(actions)} actions exceed limit of 5")
    verdict = REJECTED  # Hard rejection — no LLM override

    


    
    

      

        ④
        
OT: isolate_plc requires mode="safe-state"

        INDUSTRY_4 only
      

      

        What it checks: If isolate_plc is in the actions list,
        C5 verifies that ot_safety_flag=true on the canonical event. It adds an
        informational reason to the record so that C3 knows to inject mode="safe-state"
        when building adapter params. The SCADA plugin also hard-enforces this at execution time.
      

      
if "isolate_plc" in request.actions and event.ot_safety_flag:
    reasons.append("OT safety: isolate_plc requires mode=safe-state (C3 will inject)")
    guardrail_check.ot_safety_checked = True
    # Not a rejection — informational; C3 injects safe-state param

    


    
    

      

        ⑤
        
OT: ZTA scope must be zone-limited

        INDUSTRY_4 only
      

      

        What it checks: If the policy_update string contains
        "full ot network" or "all zones", the request is escalated.
        A blanket OT network policy change must go through human review — only zone-scoped
        changes (e.g. "Zone-B to Zone-A") are permitted without escalation.
      

      
if event.ot_safety_flag and request.policy_update:
    scope = request.policy_update.lower()
    if "full ot network" in scope or "all zones" in scope:
        reasons.append("OT ZTA scope too broad: must be zone-limited")
        verdict = ESCALATE  # → Mistral 7B semantic review

    


  


  
  

    
ESCALATE path — Mistral 7B semantic review

    

      When verdict is ESCALATE after checks ①②⑤ (not ③ — that is a hard REJECTED):
      C5 calls Mistral 7B with the full ActionRequest context and asks: "is this action proportionate
      and safe for the given threat?" The LLM resolves to either APPROVED or REJECTED.
      When OLLAMA_BASE_URL is not set, StubLLMProvider is used and returns a canned
      APPROVED response — ensuring tests work without a running Ollama instance.
    

    

      

        
✅

        
APPROVED

        
Pipeline proceeds to C3/C4 dispatch

      

      

        
❌

        
REJECTED

        
ExecutionResult with response_code=403, no dispatch

      

      

        
🤖

        
LLM REVIEW

        
Only for ESCALATE — resolves to APPROVED or REJECTED

      

    

  


  

    
GuardrailCheck schema — what C5 returns

    
{
  "check_id":          "gc-a1b2c3d4-…",
  "request_id":        "echoes ActionRequest.request_id",
  "verdict":          "APPROVED | REJECTED | ESCALATE",
  "reasons":          ["agent_confidence 0.79 below threshold 0.80"],
  "ot_safety_checked": true  // true when checks ④⑤ ran (INDUSTRY_4)
}

    
GuardrailCheck is internal — it is not published to the broker. It gates C3/C4 dispatch and is stored in the AuditRecord via audit.close_record().

WP3 / WP7 Integration

      
Per-Event WP3 Routing

      
Mixed deployment — pilot events and WP3 synthetic events handled in the same container · Routing determined per-event, not by global flag

    

  


  

    

      
How per-event routing works

      

        WP3 (STAM / D-VISOR) submits synthetic events via a dedicated input path —
        either the broker topic wp3.events.raw or the REST endpoint
        POST /api/v1/wp3/events. Both set a wp3_source=True flag stored
        in _event_cache[event_id]. When T5.4 later sends an ActionRequest
        for that event, execute_action_request() reads wp3_source from the
        cache and routes the dispatch to t53.wp3_results instead of
        t53.actions.dispatch. No global env var is needed — both real pilots and WP3
        events can flow through the same running container simultaneously.
      

    

    

      
Two input paths for WP3

      

        

          

            
Broker (push)

            
Publish to wp3.events.raw. Handled by Thread-3 in service.py. Same pika pattern as pilot tools.

          

          

            
REST (pull)

            
POST /api/v1/wp3/events — same body as /api/v1/events. Returns 202 + CanonicalEvent. Sets wp3_source=True.

          

        

        
Either path runs C1 normalisation, stores the event in SQLite and _event_cache, and publishes to t53.canonical_events for T5.4.

      

    

  


  

    
Pipeline flow — per-event WP3 routing

    

      

        wp3.events.raw
or POST /api/v1/wp3/events
        →
        C1 Normalize
wp3_source=True stored
        →
        t53.canonical_events
T5.4 receives
        →
        C5 Guardrail
        →
        C3 Policy
        →
        C4 Stubs
        →
        t53.wp3_results ✓
      

      

        ActionResult objects carry plugin="wp3_dispatch" and response_code=202.
        The dispatch payload includes "wp3_simulation": true so WP7 consumers can identify the source.
        Real pilot events arriving on pilot.events.raw simultaneously route to t53.actions.dispatch — unaffected.
      

    

  


  

    

      
Service threads

      
# service.py — three independent pika connections
Thread-1: pilot.events.raw       # real pilot tools
           → ingest_event(wp3_source=False)

Thread-2: t53.action_requests    # T5.4 ActionRequests
           → execute_action_request()
           # reads wp3_source from _event_cache

Thread-3: wp3.events.raw         # WP3 synthetic events
           → ingest_event(wp3_source=True)
